Part 1 JavaScript Foundations
Real-world analogy
Setting up your workbench before building furniture. You need the right tools (Node.js), the right workspace (project folder), and a parts list (package.json) before you cut a single piece of wood.

What it means

Before writing a single test, you need a runtime (Node.js — the engine that runs JavaScript outside a browser), a package manager (npm — fetches libraries and manages versions), and a project manifest (package.json — the parts list that says "this project needs Playwright 1.52, TypeScript 5.8, etc."). You also need an environment config so secrets like passwords aren't hardcoded in source code.

Think of package.json as a recipe card's ingredient list. When a new developer joins, they run npm install and get the exact same ingredients you used — no guessing, no "works on my machine."

package.json — project manifest with 13 npm scripts
{ "engines": { "node": ">=22.5.0" }, "scripts": { "test": "playwright test --project=chromium", "test:headed": "playwright test --project=chromium --headed", "test:debug": "playwright test --project=chromium --debug", "test:ui": "playwright test --ui", "test:smoke": "playwright test --grep @smoke --project=chromium", "test:cross": "playwright test", "report": "playwright show-report", "typecheck": "tsc --noEmit", "lint": "eslint ." } }
Why 13 scripts? Each is a different "mode" of running tests. test runs fast in headless. test:headed opens a visible browser so you can watch. test:debug lets you pause and step through code. test:ui opens Playwright's interactive dashboard. test:smoke runs only the fast critical-path tests. test:cross runs all browsers.

Learning the alphabet and grammar before writing a novel. Variables are labeled boxes, types say what goes in each box, and operators are the verbs that connect them.

What it means

const = a box you fill once and never swap (the label stays). let = a box you can refill. We almost always use const because most values don't need to change — and if they can't change, there's one fewer thing that can go wrong.

Template literals use backticks and ${...} to embed values inside strings — like a form letter where you drop in the recipient's name. Strict equality (===) checks both value AND type — 1 === '1' is false because number vs. string.

Real-world analogy
A choose-your-own-adventure book. The story branches based on decisions (if/else), repeats chapters (loops), and sometimes jumps to a specific section based on a keyword (switch).

What it means

Control flow decides which code runs and how many times. Without it, code would just run top-to-bottom, line-by-line, every time.

  • if / else if / else — pick one path based on a condition
  • switch — pick from a fixed menu of options (cleaner than a long if/else chain when you're matching one value against many possibilities)
  • for / for...of — repeat for each item in a collection
  • for...in — repeat for each key (property name) in an object
  • while — repeat until a condition becomes false (useful when you don't know how many iterations you'll need)
utils/data.helpers.ts — switch statement
export function transactionLabel(type: 'payment' | 'request'): string { switch (type) { case 'payment': return 'paid'; case 'request': return 'requested'; } }
switch reads like a lookup table: "if type is 'payment', return 'paid'; if 'request', return 'requested'." It's cleaner than if (type === 'payment') ... else if (type === 'request') ... when you have a fixed set of values to match against.
utils/data.helpers.ts — else if chain
export function categorizeAmount(amount: number) { if (amount < 10) return 'micro'; else if (amount < 100) return 'small'; else if (amount < 1000) return 'medium'; else return 'large'; }
else if creates a waterfall of checks. The first one that matches wins, and the rest are skipped. It reads exactly like English: "if it's under 10, it's micro; otherwise if it's under 100, it's small; otherwise if it's under 1000, it's medium; otherwise it's large."
utils/data.helpers.ts — while loop + for...in
// while — repeat until condition is met export async function pollUntil( check: () => Promise<boolean>, maxAttempts = 10 ): Promise<boolean> { let attempt = 0; while (attempt < maxAttempts) { if (await check()) return true; attempt++; } return false; } // for...in — iterate over object keys export function objectFieldTypes(obj: Record<string, unknown>) { const types: Record<string, string> = {}; for (const key in obj) { types[key] = typeof obj[key]; } return types; }
while keeps retrying until the check passes or we hit max attempts — you use this when you don't know how many tries you'll need (unlike for which runs a fixed number of times). for...in walks over an object's property names. If obj = { name: "Naveen", age: 30 }, the loop visits "name" then "age".
tests/e2e/cookies-storage.spec.ts — for...of loop over cookies
const cookies = await page.context().cookies(); for (const cookie of cookies) { expect(cookie.name).toBeTruthy(); expect(cookie.value).toBeDefined(); expect(cookie.domain).toBeTruthy(); }
for...of walks over each item in an array. Unlike for...in (which gives you keys/indexes), for...of gives you the actual values. Here, each cookie is a full cookie object with name, value, domain, etc.

Real-world analogy
Containers in your kitchen. Arrays are a spice rack (ordered slots). Objects are labeled jars (name + contents). Destructuring is grabbing exactly the jars you need in one motion. Spread (...) is pouring one jar's contents into another.

What it means

Data structures organize information so you can process it efficiently:

  • .find() — find the first match ("find the user named Heath")
  • .filter() — keep only items that match ("all transactions over $100")
  • .map() — transform each item ("convert every amount to a formatted currency string")
  • .reduce() — boil a list down to a single value ("sum all amounts")
  • Destructuring — unpack values in one line: const { first, last } = user
  • Spread (...) — copy/merge: { ...defaults, ...overrides }
utils/db.client.ts — .find() and .filter()
userByUsername(username: string): RwaUser | undefined { return this.read().users.find((u) => u.username === username); } transactionsForUser(userId: string): RwaTransaction[] { return this.read().transactions.filter( (t) => t.senderId === userId || t.receiverId === userId, ); }
.find() returns the first user whose username matches — or undefined if none does. .filter() returns ALL transactions where the user is either the sender or receiver. Think of .find() as "show me the first one" and .filter() as "show me all that match."
utils/data.helpers.ts — .reduce(), .map(), array destructuring
// .reduce() — boil a list to one value export function totalAmounts(amounts: number[]): number { return amounts.reduce((sum, n) => sum + n, 0); } // .map() — transform every item export function formatCurrency(amounts: number[]): string[] { return amounts.map((a) => `$${a.toFixed(2)}`); } // Array destructuring — unpack in one line export function splitFullName(fullName: string) { const [first, ...rest] = fullName.split(' '); return { first, last: rest.join(' ') }; }
.reduce() starts with 0, then adds each number one by one: [5, 10, 3] → 0+5=5 → 5+10=15 → 15+3=18. .map() transforms every item: [5, 10] → ["$5.00", "$10.00"]. Destructuring [first, ...rest] takes the first word and puts everything else into rest. "Naveen Kumar" → first="Naveen", rest=["Kumar"].

{ name: 'chromium', use: { ...devices['Desktop Chrome'] }, },
Spread ...devices['Desktop Chrome'] copies all properties (viewport size, user agent, etc.) from Playwright's built-in device preset into our project config. Like pouring a pre-mixed spice blend into your recipe instead of measuring each spice individually.

Real-world analogy
Ordering food at a restaurant. You place your order (start an async operation), then wait for it (await). You don't stand at the kitchen door. Promise.all is ordering for the whole table at once and waiting for everyone's food to arrive.

What it means

Browser actions take time — clicking, navigating, fetching data. async/await lets you write "wait for this, then do that" code that reads like a normal script. Without it, you'd need nested callbacks (the dreaded "callback hell"). Promise.all() runs multiple operations simultaneously. try/catch handles errors gracefully instead of crashing.

tests/e2e/multi-tab.spec.ts — Promise.all for popup handling
// Wait for popup AND click simultaneously const [popup] = await Promise.all([ page.waitForEvent('popup'), // Start listening BEFORE the click page.locator('#test-popup-link').click(), // This triggers the popup ]); await popup.waitForLoadState(); await expect(popup).toHaveURL(/\/bankaccounts/);
Promise.all() is critical here. If you click first and THEN start listening for the popup, you might miss it — the popup could open before your listener is ready. By wrapping both in Promise.all, the listener and click start simultaneously. It's like having one person watching the door while another knocks.
utils/login.helper.ts — try/catch for error handling
export async function ensureLoggedOut(page: Page) { await page.context().clearCookies(); try { await page.evaluate(() => { localStorage.clear(); sessionStorage.clear(); }); } catch { // page might be about:blank — that's fine } await page.goto('/signin'); }
try/catch wraps risky code. If page.evaluate() fails (because the page is about:blank and has no localStorage), the error is caught and swallowed. Without it, the entire test would crash. The empty catch says "I know this might fail, and that's OK."

Modules split code into separate files that share functionality via import/export. Without them, all code would live in one giant file. Type-only imports (import type) import just the TypeScript type — no runtime code is generated. Re-exports create convenience entry points.

Part 2 TypeScript Essentials
Real-world analogy
Labels on electrical outlets. TypeScript adds labels — "laptop only", "lamp only" — so you can't plug a toaster into the wrong socket. Mistakes are caught before the power is on (before the code runs).

What it means

TypeScript is JavaScript with a safety net. You write amount: number and the compiler ensures nobody accidentally passes a string. strict: true enables all checks. Type inference means TypeScript often knows the type without you saying it — const x = 5 is automatically number.

tsconfig.json — strict compiler config
{ "compilerOptions": { "target": "ES2022", "module": "ES2022", "strict": true, // All type-safety checks on "noUnusedLocals": true, // Dead code = compile error "noUnusedParameters": true } }
strict: true is the "all safety features ON" switch. It catches null/undefined access, implicit any types, and more. noUnusedLocals means if you declare a variable and never use it, TypeScript throws an error — no dead code allowed. ES2022 target means we can use modern JS features like top-level await and Array.at().

Real-world analogy
A form with specific field types. "Name" must be text, "Age" must be a number, "Agree to terms" must be yes/no. The form rejects mismatched input before you submit.

What it means

Array types (RwaUser[]) = "a list of users." Union types (RwaUser | undefined) = "a user, or nothing." Literal types fix exact values: 'payment' | 'request' means only those two strings are allowed — not "pament" (typo caught at compile time). Type aliases give names to complex types for reuse.

RwaUser | undefined tells the caller: "this might return nothing." TypeScript then forces the caller to handle the undefined case — you can't call .firstName on a possibly-undefined value without checking first. This prevents the dreaded "Cannot read property of undefined" runtime error.

A blueprint for a house. An interface says "every house must have a door, windows, and a roof." readonly is a load-bearing wall — once built, you can't move it.

What it means

Interfaces define contracts: "any object claiming to be an EnvConfig must have these exact properties." Optional properties (?) can be present or absent. readonly prevents accidental mutation — critical for page object locators that should never be reassigned.

config/env.ts — interface with readonly + optional
export interface EnvConfig { readonly baseURL: string; readonly apiURL: string; readonly user: { readonly username: string; readonly password: string; }; }
Every property is readonly. Once ENV is created, you can read ENV.baseURL but can't do ENV.baseURL = "something else" — the compiler blocks it. This guarantees config values stay consistent throughout the entire test run.

These interfaces describe the shape of data in the RWA database. When db.users() returns RwaUser[], TypeScript knows every item has .username, .firstName, .balance etc. You get autocomplete for free, and typos like user.usrname are caught instantly.

Real-world analogy
A vending machine that works with any product. You don't need a separate machine for sodas and snacks — one machine handles both. get<Soda>() gives you a soda, get<Snack>() gives you a snack, same machine.

What it means

Generics are type variables — placeholders that the caller fills in. Instead of writing getUsers(), getTransactions(), getContacts() separately, you write get<T>() once and let the caller specify T. The function stays type-safe no matter what T is.

utils/api.client.ts — generic API methods
async get<T>(path: string): Promise<T> { const res = await this.request.get(`${this.baseUrl}${path}`); if (!res.ok()) throw new ApiError(...); return (await res.json()) as T; } // Caller specifies the exact response type: const data = await api.get<{ results: Array<{ username: string }> }>('/users'); // data.results[0].username — fully typed, autocomplete works

Real-world analogy
Vehicle types. BasePage is the abstract concept "vehicle" — it defines every vehicle must have an engine and wheels, but you can't drive "a vehicle." SigninPage is a "sedan" — a concrete vehicle you can actually drive.

What it means

Abstract classes define a template: "every page must implement path and waitForLoaded()." You can't create a BasePage directly — you must subclass it. Inheritance means SigninPage gets open(), sidenav, topnav for free from BasePage. Access modifiers: public = anyone can use it, private = only this class, readonly = set once, never change.

pages/base.page.ts — abstract base class
export abstract class BasePage { readonly sidenav: SideNavComponent; readonly topnav: TopNavComponent; constructor(public readonly page: Page) { this.sidenav = new SideNavComponent(page); this.topnav = new TopNavComponent(page); } abstract readonly path: string; abstract waitForLoaded(): Promise<void>; async open(): Promise<void> { await this.page.goto(this.path); await this.waitForLoaded(); } }
abstract means "I declare this exists, but each subclass must implement it." BasePage says "every page has a path and a waitForLoaded()" but doesn't know the specifics. open() is concrete — it navigates to this.path and waits. Since every subclass inherits open(), you write the navigation logic once. Component composition: every page automatically gets sidenav and topnav access.
pages/signin.page.ts — concrete subclass
export class SigninPage extends BasePage { readonly path = '/signin'; readonly username = this.page.getByLabel('Username'); readonly password = this.page.getByLabel('Password'); readonly submit = this.page.getByRole('button', { name: 'Sign In' }); async waitForLoaded() { await this.submit.waitFor(); } async login(user: string, pass: string) { await this.username.fill(user); await this.password.fill(pass); await this.submit.click(); } }
extends BasePage means SigninPage inherits open(), sidenav, topnav. It provides its own path (/signin) and waitForLoaded() (wait for the submit button). Each readonly locator is set once during construction and never reassigned. The login() method encapsulates the three steps into one reusable call.

Part 3 Playwright Core
Real-world analogy
A robot quality inspector on an assembly line. Instead of a human clicking every button after every code change, the robot does it in seconds — consistently, tirelessly, and at 3am if needed.

What it means

Playwright's architecture has three layers: Browser (the whole application — Chrome, Firefox, or WebKit), BrowserContext (an isolated session — like an incognito window with its own cookies and storage), and Page (a single tab within a context). Multiple pages can share a context (shared cookies), or each can have its own (isolated).

fixtures/test.ts — Browser → Context → Page hierarchy
// Worker-scoped: ONE context per worker (shared cookies) sharedContext: [ async ({ browser }, use) => { const context = await browser.newContext({ baseURL: ENV.baseURL }); await use(context); await context.close(); }, { scope: 'worker' }, ], // ONE page inside that context (all tests share this tab) sharedPage: [ async ({ sharedContext }, use) => { const page = await sharedContext.newPage(); await use(page); }, { scope: 'worker' }, ],
browser → context → page: like Chrome → incognito window → tab. The worker scope means this context is created once and shared across all tests in the same worker process — they share cookies, localStorage, and login state. This is why we log in once and all tests are already authenticated.

What it means

A test has three parts: Arrange (set up the page), Act (do something), Assert (verify the result). test('name', async () => { ... }) wraps this. expect(thing).toBeVisible() is the assertion — if it's wrong, the test fails with a clear error message.

The test title reads like a sentence: "should sign in successfully." The body follows Arrange-Act-Assert. Fixtures (signinPage) are injected automatically — no setup code needed in the test itself. If any assertion fails, Playwright shows exactly what went wrong: expected "visible", got "hidden."

Real-world analogy
Giving directions to find someone in a crowd. "The person in the red hat" (CSS selector) works, but "the person holding the 'Sign Up' sign" (role/label locator) is more reliable — even if they change their hat.

What it means

Playwright offers a hierarchy of locator strategies, from most resilient to least:

  • getByRole() — find by accessibility role: button, link, heading. Most resilient — survives HTML restructuring
  • getByLabel() — find form fields by their label text
  • getByTestId() — find by a data-test attribute (custom, stable hook)
  • locator() — CSS selector, least resilient but sometimes necessary

You can chain (.locator('input')), filter (.filter({ hasText })), use list ops (.first(), .nth()), and compose (.or()).

pages/signin.page.ts — all four locator strategies in one file
// getByLabel — find by the form field's label text readonly username = this.page.getByLabel('Username'); // getByRole — find by accessibility role + name readonly submit = this.page.getByRole('button', { name: 'Sign In' }); // getByTestId — find by data-test attribute readonly error = this.page.getByTestId('signin-error'); // CSS locator — text selector for validation message readonly usernameRequired = this.page.locator('text=Username is required');
Each strategy has its place. getByLabel('Username') is how a real user finds the field — by reading its label. getByRole('button') is how a screen reader finds it. getByTestId uses a custom attribute developers add specifically for testing. locator('text=...') is a last resort when the element has no role, label, or test ID.
pages/transaction.page.ts — chaining, filtering, list operations
// Chaining — narrow down from parent to child readonly amountInput = this.page.getByTestId('transaction-create-amount-input') .locator('input'); // Filtering — find user by name within the list async selectUser(name: string) { await this.page.locator('[data-test*="user-list-item"]') .filter({ hasText: name }).first().click(); }
Chaining: getByTestId('...') finds the container, then .locator('input') finds the actual input inside it. Filtering: .filter({ hasText: name }) narrows the list to items containing the user's name. .first() takes the first match. This reads like: "find all user list items, keep only those containing 'Heath', click the first one."

Real-world analogy
A quality inspector with a checklist. They check: "Is the label visible?" "Does it say 'Approved'?" "Is the button grayed out?" Soft assertions note ALL defects on one pass instead of stopping at the first.

What it means

Web-first assertions auto-retry until the condition is met or timeout. This handles timing naturally — you don't need sleep(2000). Soft assertions (expect.soft()) collect failures without stopping the test. Visual assertions (toHaveScreenshot()) compare pixel-by-pixel against a baseline image.

Real-world analogy
A mail room sorting machine. You can intercept any letter (request) and: deliver it as-is (continue), rewrite it (modify headers), replace it with a fake (fulfill), or shred it (abort). The sender and receiver never know.

What it means

page.route() intercepts network requests matching a pattern. Four options: abort (block it), continue (pass through, optionally modify headers), fulfill (return fake data — the server is never contacted), fetch + modify (get the real response, change it, then forward it). This lets you test edge cases without modifying the server.

tests/practice/network-mocking.spec.ts — all four interception modes
// ABORT — block all images await page.route('**/*', async (route) => { if (route.request().resourceType() === 'image') await route.abort(); else await route.continue(); }); // CONTINUE — add custom headers to a request await page.route('**/todos/2', async (route) => { const headers = { ...route.request().headers(), 'x-custom-header': 'added-by-playwright', }; await route.continue({ headers }); }); // FULFILL — return fake data (server never contacted) await page.route('**/api/mock-data', (route) => route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify({ items: ['alpha', 'beta'] }), }), ); // FETCH + MODIFY — get real response, change it await page.route('**/todos/1', async (route) => { const response = await route.fetch(); const json = await response.json(); json.title = 'INTERCEPTED BY PLAYWRIGHT'; await route.fulfill({ response, body: JSON.stringify(json) }); });
