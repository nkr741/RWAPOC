Phase 1 How the Framework is Built
You're a waiter at a restaurant. A customer says "I want coffee." You don't tell them "Walk to the kitchen, open cabinet 3, grab the filter, fill the machine..." — you just bring the coffee. The customer doesn't need to know HOW the kitchen works.

POM is the same idea. A page object is the "waiter" — it knows where every button, input, and link is on a page and how to interact with them. The test (the "customer") just says signinPage.login('user', 'pass') and never touches a single HTML element directly.

Why it matters: If the developers change the login button from <button> to <a>, you fix ONE file (the page object), not 20 test files. The tests themselves don't change at all.

In this POC, every page of the RWA app has its own class: SigninPage, HomePage, TransactionPage, BankAccountPage, etc. Each extends BasePage which gives it a standard open() method and access to the sidebar/topbar navigation.

The sidebar menu appears on EVERY page of the app — Home, Bank Accounts, Settings, everywhere. Instead of teaching each page object how to click "Home" or "Logout" separately, you write it once in a SideNavComponent and hand it to every page. Like installing the same remote control in every room of your house.

SideNavComponent and TopNavComponent are shared "keyword" classes. Methods like navigateHome(), logout(), clickNewTransaction() are keywords — plain English actions any manual tester would understand.

Every page object gets these keywords automatically through composition (the page HAS a sidenav, not IS a sidenav). So homePage.sidenav.logout() and settingsPage.sidenav.logout() both work — same keyword, different pages.

When you sit down at a fancy restaurant, the table is already set — plates, glasses, cutlery. You didn't ask for them; they're just there. If you don't use the soup spoon, that's fine, it doesn't cost anything extra. Fixtures work the same way.

In fixtures/test.ts, we register every page object, API client, and database client. A test simply says async ({ signinPage, sidenav, authedApi }) => and Playwright creates exactly what the test needs. If a test doesn't mention bankAccountPage, it's never created — zero overhead.

This is dependency injection: the test declares what it needs, the framework provides it. The test never does new SigninPage(page) itself — the fixture handles creation, setup, and cleanup.

Imagine filling out a form during testing. If you always type "John Smith" with email "john@test.com", your tests only prove that one specific set of data works. Faker is like having a random name generator that gives you "Priya Patel", "Carlos Rivera", "Aisha Bello" — different realistic data every time.

@faker-js/faker generates unique bank names, routing numbers, usernames, passwords, and transaction amounts per run. No two test runs use identical data, which catches bugs that hardcoded values would miss (like a field that breaks on special characters).

Static data (like the login credentials) comes from environment variables. Dynamic data (like bank account details) is generated fresh. Factory functions (like SignupData.newUser()) generate unique data on every call — useful when a test creates multiple users.

Finding an element on a webpage is like finding a person in a crowd. You can describe them by their role ("the cashier"), their name tag ("Hi, I'm Sarah"), or their outfit ("the person in the red shirt, third from left"). Some descriptions are fragile ("third person from left" — what if someone moves?), others are stable ("the cashier" — there's always one).

Playwright offers a priority hierarchy:

getByRole('button', { name: 'Sign In' }) — finds by what it IS (a button labeled "Sign In"). Most resilient.

getByLabel('Username') — finds by its form label. Great for inputs.

getByTestId('sidenav-home') — finds by a data-test attribute developers add specifically for testing. Reliable fallback.

page.locator('[data-test*="transaction-item"]') — CSS selector. Last resort, but sometimes necessary for lists of items.

The RWA app uses data-test (not data-testid), so Playwright's config sets testIdAttribute: 'data-test' to make getByTestId() work correctly.

A hard assertion is like a security guard at a door: if you don't have ID, you're stopped immediately — nobody behind you gets in either. A soft assertion is like a building inspector: they note every problem (cracked window, loose railing, bad wiring) and hand you the full list at the end. Neither stops the inspection early.

Auto-retrying assertions are the key difference from other frameworks. await expect(element).toBeVisible() doesn't check once and fail — it keeps checking for up to 10 seconds. Web pages are dynamic; elements appear after API calls, animations, or React re-renders. Playwright waits patiently instead of failing on timing.

expect.soft() collects failures without stopping the test. Use it when you want to check 10 things on a page and see ALL failures at once, not just the first one.

Most test frameworks open a fresh browser window for every single test. That's like closing and reopening Chrome 70+ times during a test run. Our approach: open Chrome once, run all tests in the same window, like a real user would browse.

This is done through worker-scoped fixtures. sharedContext and sharedPage are created once per worker and survive across all tests. The built-in page fixture is overridden to point to sharedPage — so tests think they have their own page, but they're all sharing one.

Trade-off: Tests run sequentially (can't run 5 tests at once in one window). For speed, you'd switch to workers: 4 with full isolation per test, or use sharding across CI machines.

Writing JavaScript without TypeScript is like driving without a dashboard — you have no speedometer, no fuel gauge, no warning lights. TypeScript adds those gauges. ESLint adds the lane departure warning — it stops you from doing things that technically work but cause problems later.

TypeScript catches bugs before you run anything. Misspell signinPage.usernme instead of .username? The editor shows a red squiggle instantly. No more discovering typos at 2am in CI.

ESLint with playwright plugin enforces best practices. It blocks waitForTimeout() (arbitrary sleeps), networkidle (unreliable waits), and conditionals in tests (if/else makes tests non-deterministic). Every JSON.parse() call has a type assertion to prevent any from leaking through the codebase.

The project has zero ESLint errors and zero TypeScript errors across all files.

Phase 2 Authentication & State
Imagine 70 people need to enter a building that requires ID check. Instead of each person going through security separately, ONE person goes through, gets a visitor badge cloned 70 times, and hands one to each person. Everyone walks right in.

auth.setup.ts logs in once, then saves the cookies and localStorage to a JSON file (storageState). Every subsequent test loads that saved state — it starts already logged in. This saves 2-3 seconds per test (no login page, no typing, no waiting for redirect).

The setup runs before all other test projects via the dependencies: ['setup'] config. Chromium, Firefox, and WebKit all reuse the same auth file.

Before entering a room, you check if the door is already open. If it is, you walk through. If it's locked, you use your key. You don't use your key on an open door — that's wasted effort.

ensureLoggedIn() checks the current page state. If the sidenav is visible, the user is already logged in — do nothing. If the sign-in button is visible, perform the login. This avoids redundant login flows in a shared browser window.

It uses signinBtn.or(sidenav).waitFor() — a composite locator that matches whichever appears first. No guessing, no try/catch, no arbitrary waits.

ensureLoggedOut() does the reverse: clears cookies, clears storage, and navigates to the signin page.

Your browser has three places to store information. Cookies are like a wristband at a concert — the server gave it to you, it proves who you are, and the server checks it every time. localStorage is like a notebook you keep in your desk — it stays there even after you leave and come back. sessionStorage is like a sticky note on your monitor — it's gone the moment you close that browser tab.

The 16 tests in this spec cover everything: reading httpOnly cookies (which JavaScript can't see but Playwright can), injecting custom cookies, clearing cookies to break auth, reading/writing localStorage, verifying sessionStorage doesn't leak between tabs, and using addInitScript to pre-populate storage before the page even loads.

The key Playwright APIs: context.cookies(), context.addCookies(), context.clearCookies(), and page.evaluate(() => localStorage.getItem(...)).

Imagine a pop-up ad that appears randomly on any page. You can't predict when it'll show up. Instead of checking for it at the start of every test, you install an ad blocker that automatically clicks "dismiss" whenever it appears. That's addLocatorHandler.

The RWA has a 3-step onboarding dialog that pops up for new users. It can appear on any page, at any time. registerOnboardingHandler() sets up a rule: "whenever the onboarding dialog becomes visible, click through all three steps and dismiss it."

This is registered once in the fixture setup. Every test in the entire suite is protected automatically. No test ever needs to think about onboarding — the handler takes care of it.

The same pattern works for cookie consent banners, chat widgets, GDPR popups, or any overlay that appears unpredictably.

Phase 3 User Interactions
Forms are the primary way users give information to an app. Testing forms means verifying every input type works: text boxes, checkboxes (on/off toggles), radio buttons (pick one from a group), and dropdowns (select from a list).

check() is smarter than click() for checkboxes: calling check() on an already-checked box does nothing (idempotent). click() would uncheck it. Same idea with uncheck().

selectOption() works three ways: by value ('1'), by visible text ({ label: 'Option 2' }), or by position ({ index: 1 }). The test covers all three. For Material UI dropdowns (not native <select>), you click to open, then click the option — different flow, same result.

Radio buttons automatically deselect others in their group when one is selected, and the test verifies this behavior.

Native browser dialogs (alert, confirm, prompt) are like someone tapping you on the shoulder — everything stops until you respond. They're not part of the webpage DOM; they're OS-level popups that Playwright handles through events.

You must set up a listener before triggering the dialog: page.once('dialog', callback). Inside the callback, you can accept(), dismiss(), or accept('input value') for prompts.

page.once() handles one dialog and auto-removes itself. page.on() stays active for multiple sequential dialogs. The POC tests both patterns, plus dismissing (returning false/null).

7 tests cover: alert accept, confirm accept, confirm dismiss, prompt with input, prompt dismiss, auto-dismiss onboarding overlay, and three sequential dialogs in a row.

All tabs in one browser window share the same login session. Open Gmail in two tabs — both show your inbox. Navigate one tab to Calendar — the other still shows Gmail. Create an email in tab 1, refresh tab 2, it shows up. That's exactly what we test.

Opening a tab: sharedContext.newPage() creates a new tab in the same browser context. Shared cookies mean shared auth — the new tab is already logged in.

Independent navigation: Each tab has its own URL and DOM. Moving tab 1 to /notifications doesn't change tab 2 sitting on /bankaccounts.

Cross-tab sync: Tab 1 makes a payment. Tab 2 reloads and sees it. This verifies the server persisted the data correctly — not Playwright magic, just how web apps work.

Popups: When a target="_blank" link opens a new window, you capture it with page.waitForEvent('popup') set up BEFORE clicking the link. Promise.all ensures the listener is ready before the click fires.

For POM on dynamic tabs, we instantiate page objects directly: new SideNavComponent(secondTab). The locators still live in the page object class — not in the test.

An iframe is a webpage inside a webpage — like a picture frame on a wall, except the picture is a live, interactive mini-website. You can't just click inside a painting on the wall; you need to "step into" the frame first.

page.frameLocator('#child') gives you a handle to interact with elements inside the iframe. From there, frame.locator('#input').fill('Hello') works just like the main page. Nested iframes chain: page.frameLocator('#outer').frameLocator('#inner').

The clever part: The RWA app has NO iframes. So we created synthetic test pages using page.route() — intercepting HTTP requests and serving custom HTML with embedded iframes. The browser doesn't know the difference. 8 iframe tests, zero changes to the actual app.

Tests cover: basic iframe interaction, frame lookup by name/URL, enumerating all frames, nested iframes, cross-frame postMessage communication, embedding the RWA inside an iframe, and multi-tab + iframe combined.

Basic actions are clicking and typing. Advanced actions are everything else a human does: hovering to reveal a tooltip, pressing keyboard shortcuts (Ctrl+A to select all), dragging a file from one folder to another, or clicking at a specific spot on a map.

Hover: element.hover() moves the mouse over an element, revealing hidden content (tooltips, dropdown menus, hover effects).

Keyboard: keyboard.type('Hello', { delay: 30 }) simulates human typing speed. keyboard.press('Control+A') sends keyboard shortcuts.

Drag-and-drop: elementA.dragTo(elementB) implements HTML5 native drag. Works with most drag libraries (React DnD, SortableJS).

Mouse coordinates: page.mouse.click(x, y) clicks at exact pixel coordinates. Essential for canvas elements, image maps, or click regions where there's no DOM element to target.

Normally when you click "Choose File" on a website, your OS opens a file picker dialog. In automated testing, you can't interact with OS dialogs. So Playwright skips the dialog entirely and injects the file directly into the input element — like sliding a document under the door instead of walking through it.

Upload from memory: setInputFiles({ name: 'test.txt', buffer: Buffer.from('content') }) creates a file on the fly without touching the filesystem. Clean, fast, no temp files to manage.

Upload from disk: setInputFiles('/path/to/file.txt') uses a real file. Useful for testing file-size limits or binary formats like PDFs.

Download: page.waitForEvent('download') captures the download event, then download.saveAs(path) saves it. You verify the filename, size, and content.

Phase 4 API & Network
UI testing is like ordering food at a restaurant and checking the dish looks right. API testing is like going into the kitchen and checking the chef is following the recipe correctly. Even if the waiter serves the dish beautifully, the kitchen might be cutting corners.

Playwright has a built-in HTTP client (APIRequestContext) that sends real HTTP requests — no browser needed. The ApiClient class wraps it with typed methods: get<T>(), post(), delete(). If a request fails, ApiError tells you exactly which endpoint returned which status code.

22 API tests cover: users (list, profile, search, create, login), transactions (list, public feed, create, get by ID), bank accounts (CRUD + auth check), contacts, likes, comments, and notifications.

The authedApi fixture auto-authenticates before each test. The api fixture stays unauthenticated — used to verify that protected endpoints return 401.

Imagine you could intercept every letter sent from your house to the post office. You could: block junk mail (route.abort), modify the return address (route.continue with changed headers), replace the letter entirely with a fake one (route.fulfill), or open the real letter, change one word, and reseal it (route.fetch + modify).

page.route() intercepts HTTP requests at the network level. Four patterns:

Abort: Block all images to test how the page looks without them, or block analytics scripts to speed up tests.

Continue with modifications: Add custom headers to requests — useful for testing auth header forwarding or feature flags.

Fulfill: Return completely fake data. The backend doesn't even get called. Perfect for testing edge cases (empty lists, error responses, massive datasets) without setting up real data.

Fetch + modify: Let the real request go through, but tweak the response. Test how the UI handles a slightly different data shape without changing the backend.

This is also how we created synthetic iframe test pages — route.fulfill() served custom HTML for URLs that don't really exist on the server.

When you transfer money using a banking app: (1) you see "Transfer successful" on screen, (2) the bank's API records the transaction, (3) the database stores it permanently. If any layer lies — the screen says success but the API didn't process it, or the API returns OK but the database didn't write it — you have a bug that single-layer testing would never catch.

This single test verifies all three layers in sequence:

Layer 1 — UI: Log in, navigate to new transaction, select a user, enter amount, click pay, see the success alert.

Layer 2 — API: Call GET /transactions and find the transaction we just created by its description.

Layer 3 — Database: Read the lowdb JSON file directly and verify the transaction record exists with the correct sender, amount, and status.

Each layer uses test.step() so the HTML report shows exactly which layer failed — "UI worked, API worked, DB failed" — without reading through all assertions.

Phase 5 Visual & Cross-Browser
You take a photo of your living room today. Next week, after the cleaners come, you take another photo and compare them pixel by pixel. If the couch moved 2 inches or a painting is crooked, the comparison catches it. Visual regression testing does this for web pages.

toHaveScreenshot('name.png') compares the current page (or element) against a saved baseline image. If they differ beyond a threshold, the test fails and shows you a visual diff — red highlights where pixels changed.

First run creates the baseline. Subsequent runs compare against it. If the change is intentional (new design), run with --update-snapshots to save new baselines.

We use page.setContent() with hardcoded HTML for deterministic baselines — no dynamic data (timestamps, usernames) to cause false positives.

Your website works perfectly in Chrome. But a customer using Safari sees a broken layout, and a Firefox user can't click the submit button. Cross-browser testing runs the same tests in all three browsers to catch these differences before your users do.

Playwright bundles its own browser binaries — Chromium, Firefox, and WebKit (Safari's engine). No WebDriver, no driver version mismatches, no browser compatibility issues. npx playwright install downloads exact versions tested against your Playwright version.

Three projects in the config: chromium (primary), firefox, webkit. The same test code runs identically on all three. Run all with npm run test:cross-browser or individual browsers with --project=firefox.

For mobile testing, Playwright offers device presets like devices['iPhone 13'] that set viewport size, user agent, and touch mode. No emulators needed — the desktop browser resizes to match.

You have 300 exam papers to grade. One teacher takes 3 hours. Three teachers split the stack into thirds and finish in 1 hour. That's sharding — splitting the work across multiple machines.

--shard=1/3 runs the first third of test files, --shard=2/3 the second, --shard=3/3 the last. Each shard is a completely independent process — different CI machine, different Node process. After all finish, merge-reports combines the results into one HTML report.

Sharding is different from workers. Workers run tests in parallel within one machine (multiple CPUs). Shards run tests in parallel across machines. You can combine both: 3 shards with 4 workers each = 12 parallel test streams.

For CI, a GitHub Actions matrix strategy creates one job per shard. Each uploads its blob report as an artifact, and a final job merges them.

Phase 6 Debugging & Real-World Patterns
When a test fails in CI at 3am, you need to see exactly what the browser saw. Playwright's Trace Viewer is like a flight recorder (black box) for your test — it captures a timeline of every click, every network request, every DOM change, and lets you replay it frame by frame.

Debug mode (--debug): Opens the Playwright Inspector with step-through execution, locator highlighting, and a live DOM explorer. Like Chrome DevTools but for your test script.

Trace Viewer: A zip file containing screenshots at every step, network logs, console output, and DOM snapshots. Download from CI artifacts, open with npx playwright show-trace trace.zip. You see exactly what the test saw.

UI mode (--ui): Interactive test runner with watch mode. Change code, tests re-run automatically. See pass/fail in real time with screenshots.

page.pause() in code freezes the test at that exact point and opens the inspector.

Your app runs on different servers: localhost for development, staging.company.com for QA, app.company.com for production. Each has different URLs and credentials. Environment variables are like a settings dial — turn it to "staging" and every test automatically points to the right server.

config/env.ts reads from a .env file (gitignored, never committed) and exports a typed ENV object. Required variables (QA_USER, QA_PASSWORD) throw immediately if missing — fail fast with a clear error instead of timing out on a wrong URL 5 minutes later.

Optional variables have defaults: BASE_URL defaults to http://localhost:3000. In CI, environment variables override the file.

The EnvConfig interface guarantees type safety: misspell baseURL as baseUrl anywhere in the codebase, and TypeScript catches it at compile time.

After running 113 tests, you need answers fast: what passed? What failed? Why? A test report is like a medical lab report — it summarizes all results, highlights the abnormals, and gives you enough detail to diagnose the problem.

List reporter: Real-time terminal output during the run. Shows each test as it starts and finishes.

HTML reporter: A self-contained web page with screenshots, traces, timing data, and step-by-step breakdowns. Open with npm run report. Shows flaky tests (passed on retry) vs failed tests (failed all attempts).

JUnit reporter: XML format for CI systems (Jenkins, Azure DevOps, GitLab). Enables test trend dashboards and failure tracking.

Retries: retries: 2 in CI means a failed test runs up to 3 times total. trace: 'on-first-retry' captures a trace only when a test needs retrying — this is the trace you debug, not the successful run.
