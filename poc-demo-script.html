What to Show

What to Say — Opening
Say: "Before we write a single test, let me show you why TypeScript is non-negotiable for serious test automation. JavaScript is like driving without a dashboard — you don't know your speed, your fuel level, or if the engine is overheating until something breaks. TypeScript adds that dashboard. How to Explain — Walk Through the Code Line by Line
Explain: Point to the import * as dotenv line. "This loads environment variables from a .env file into process.env. In production, these come from CI secrets. Locally, from a .env file you never commit to git."
Show: Highlight the interface EnvConfig block:
export interface EnvConfig {
  readonly baseURL: string;
  readonly apiURL: string;
  readonly user: { readonly username: string; readonly password: string };
}
Say: "This interface is a contract. It says: 'Every environment configuration MUST have a baseURL that's a string, an apiURL that's a string, and a user object with username and password.' If anyone tries to access ENV.databaseURL and we didn't define it in the interface — TypeScript catches it at compile time, not after 50 tests run."
Explain: Point to the readonly keyword on every property. "This means once the config is created, nobody can accidentally write ENV.baseURL = 'wrong-url' in a test. TypeScript makes the config immutable. In JavaScript, you'd need Object.freeze() and hope nobody forgets it."
Show: Highlight the req() function:
function req(name: string): string {
  const value = process.env[name];
  if (!value) throw new Error(`Missing required environment variable: ${name}`);
  return value;
}
Say: "This is a fail-fast guard. The function signature says: 'Give me a string, I'll give you a string back.' But process.env[name] returns string | undefined. The if (!value) throw narrows the type — after that check, TypeScript knows value is definitely a string, not undefined. This is called type narrowing."
Say: "In plain JavaScript, if QA_USER is missing, you get undefined. Your test fills the username field with undefined. The login fails. The test fails with 'Element not found: sidenav-user-full-name.' You spend 20 minutes debugging only to discover the env var was missing. With this function, you get 'Missing required environment variable: QA_USER' on the first line of execution. Zero detective work."
Show: Highlight the ENV object at the bottom:
export const ENV: EnvConfig = {
  baseURL: process.env.BASE_URL || 'http://localhost:3000',
  apiURL: process.env.API_URL || 'http://localhost:3001',
  user: { username: req('QA_USER'), password: req('QA_PASSWORD') },
};
Say: "Notice the pattern: baseURL and apiURL have defaults with the || operator — if no env var is set, fall back to localhost. But username and password go through req() — no defaults. Credentials MUST be explicitly provided. This is intentional. You never want to accidentally test against a hardcoded password that gets committed to source control."
How to Explain — TypeScript Concepts in Action
Say: "Let me show you the five TypeScript features we use most in this framework, all visible in the files we'll open today:"
Explain each concept with a real example:

1. Interfaces — EnvConfig in env.ts. "An interface is a shape definition. It doesn't generate any JavaScript — it only exists at compile time. But it prevents you from making a typo in a property name."

2. Type annotations — function req(name: string): string. "The return type : string is a promise. If you accidentally return a number, TypeScript catches it."

3. Generics — async get<T>(path: string): Promise<T> in api.client.ts. "The <T> means 'whatever type you tell me, I'll return that type.' So api.get<User[]>('/users') returns User[], and api.get<Transaction>('/transactions/123') returns Transaction. Same function, different return types, all type-safe."

4. Abstract classes — abstract class BasePage in base.page.ts. "You can't create a new BasePage(). You must extend it and implement the abstract methods. This forces every page object to define path and waitForLoaded()."

5. Access modifiers — private readonly homeLink in sidenav.component.ts. "Tests can call sidenav.navigateHome() but can never access sidenav.homeLink directly. The selector is an implementation detail, hidden behind a keyword method."
How to Explain — Real-World Analogy
Say: "Think of TypeScript like a building blueprint. You can build a house without a blueprint — just grab bricks and start stacking. It'll be faster at first. But when you add a second floor, you don't know if the foundation can hold it. TypeScript is the blueprint: slower to draw, but you catch structural problems before you pour the concrete, not after."
What to Show — Compiler in Action
Show: Run npx tsc --noEmit in the terminal. "Zero errors. Every single file in this project compiles cleanly. No any types allowed — we have no-explicit-any as an ESLint rule. This is the bar for production-grade test code."
Anticipated Q&A
Q: "Isn't TypeScript slower to write than JavaScript?"
A: "Yes, initially. You spend 10% more time writing types upfront. But you save 50% of debugging time. A senior engineer on our team said: 'I spend 2 hours writing TypeScript, or 2 hours writing JavaScript plus 4 hours debugging undefined is not a function.' The math is clear."
Q: "What does as const do?"
A: "It makes an object deeply readonly and narrows the types to literal values. { amount: '5' } has type string. { amount: '5' } as const has type '5' — the literal string '5'. This prevents accidental mutation in test data."
Q: "Do I need to know TypeScript before learning Playwright?"
A: "No. Start with JavaScript, then add types gradually. Playwright works with both. But for a team project — especially one with 100+ tests — TypeScript pays for itself in the first month."
Common Pitfalls
Pitfall 1: Using any to silence errors. This defeats the purpose. If you don't know the type, use unknown and narrow it.
Pitfall 2: Not handling undefined. process.env[name] returns string | undefined. Always check before using.
Pitfall 3: Committing .env files to git. Add .env to .gitignore immediately. Credentials in source control = security incident.
Key Takeaways
Key takeaways: (1) TypeScript = compile-time safety net. (2) Interfaces define contracts for your data shapes. (3) readonly prevents accidental mutation. (4) Fail-fast with req() beats silent undefined propagation. (5) Zero any, zero ESLint errors, zero TypeScript errors = production-grade.

03Playwright Fundamentals & Architecture~30 min
What to Show
Open: playwright.config.ts — show the entire file. Keep it visible throughout this module.
What to Say — Opening
Say: "This single file controls everything — which browsers to use, how fast to run, how many retries, what reporters to generate, what timeouts to set. If the framework were a car, this is the dashboard AND the engine configuration combined."
How to Explain — Global Settings, Line by Line
Show: Highlight each setting and explain:
testDir: './tests',         // where Playwright looks for spec files
fullyParallel: false,       // tests in a file run sequentially
workers: 1,                 // one browser window at a time
retries: process.env.CI ? 2 : 0,  // retry in CI, not locally
forbidOnly: !!process.env.CI,     // prevent .only from reaching CI
Say: "fullyParallel: false — this means tests within a single spec file run in the order they're written. Test 1 completes before test 2 starts. This is critical when tests share state through a sharedPage fixture — test 1 logs in, test 2 assumes it's logged in. workers: 1 — only one browser window. This is deliberate for local development. We share a single browser context across all tests. No repeated logins, no isolated pages. Fast and predictable. For CI speed, we use sharding across multiple machines instead of multiple workers on one machine. retries: process.env.CI ? 2 : 0 — if we're in CI, retry failed tests up to 2 times. Locally, zero retries. Why? Locally, a failure is a real bug — you want to see it immediately. In CI, infrastructure flakes happen — a DNS timeout, a slow container startup. Retries absorb those. forbidOnly: !!process.env.CI — if someone accidentally commits test.only('my test'), CI will fail with a clear error instead of silently running only one test and reporting 'all tests pass.' This has saved us multiple times."
How to Explain — The use Block
Show:
use: {
  baseURL: ENV.baseURL,           // all goto() calls are relative to this
  testIdAttribute: 'data-test',   // getByTestId looks for data-test, not data-testid
  trace: 'on-first-retry',        // record trace only on first retry
  screenshot: 'only-on-failure',  // capture screenshot only when test fails
  video: 'retain-on-failure',     // keep video recording only for failed tests
  actionTimeout: 15_000,          // each click/fill waits up to 15 seconds
  navigationTimeout: 30_000,      // page.goto waits up to 30 seconds
},
Say: "baseURL means page.goto('/signin') becomes page.goto('http://localhost:3000/signin'). No hardcoded URLs in tests. testIdAttribute: 'data-test' — this is crucial. By default, Playwright's getByTestId() looks for data-testid. But the RWA app uses data-test. One line in the config fixes it for every test. Without this, every getByTestId call would silently find nothing. trace: 'on-first-retry' — this is the performance-vs-debugging tradeoff. Recording traces on every test adds 10-15% overhead. Recording only on retry means: passing tests have zero overhead, and failed tests get full diagnostics on the retry. Best of both worlds. screenshot: 'only-on-failure' and video: 'retain-on-failure' — same principle. We only collect artifacts when they're needed. No wasted disk space on passing tests."
How to Explain — Timeout Hierarchy
Explain: "Playwright has FOUR levels of timeout, from largest to smallest:"
timeout: 60_000,          // Test-level: the entire test must complete in 60s
expect: { timeout: 10_000 }, // Assertion: expect(locator) retries for 10s
actionTimeout: 15_000,    // Action: each click/fill waits 15s for the element
navigationTimeout: 30_000 // Navigation: page.goto waits 30s for the page
Say: "The rule: test timeout > navigation timeout > action timeout > assertion timeout. If assertion is larger than test, the assertion timeout is meaningless — the test dies first. Getting this hierarchy wrong is a common source of confusing failures."
How to Explain — Projects (the big one)
Show: Scroll to the projects array:

  },

    name: 'webkit',
    dependencies: ['setup'],
    use: { ...devices['Desktop Safari'] },

  },
],
Say: "Six projects — think of them as six different execution lanes on a highway, each with its own rules. api — matches tests/api/*.spec.ts. No browser, no dependencies. Pure HTTP tests. The fastest lane. setup — matches tests/setup/auth.setup.ts. This runs ONCE, logs in, saves the auth state to a JSON file. It's the on-ramp that every browser test lane depends on. practice — matches tests/practice/*.spec.ts. Standalone demo tests. No dependency on setup because they hit external sites, not the RWA. chromium / firefox / webkit — these three all ignore api, setup, and practice files. They all depend on setup. This means: Playwright runs setup first, then runs the same UI tests on three different browser engines. Same code, three browsers, zero code changes. The dependencies: ['setup'] creates a DAG — a directed acyclic graph. Playwright resolves it: setup runs first, browser projects run after. If setup fails, browser projects are skipped. No orphaned runs."
How to Explain — Browser Architecture
Explain with a diagram:
Browser (one per worker)
  └── BrowserContext (like an incognito window — cookies, storage, etc.)
       └── Page (a single tab)
            └── Locator (a pointer to an element — evaluated lazily)

Key rules:
• Different contexts = fully isolated (no shared cookies)
• Same context, different pages = shared cookies (multi-tab testing)
• Locators are LAZY — they don't find the element until you act on it
Say: "The most important concept: Locators are lazy. When you write page.getByRole('button', { name: 'Submit' }), nothing happens. No DOM query. No HTTP call. The locator is just a description — 'the button named Submit.' The actual DOM lookup happens when you call .click() or .fill() or expect().toBeVisible(). This is why locators never go stale — they re-evaluate on every action. In Selenium, a stale element reference crashes your test. In Playwright, it literally cannot happen."
How to Explain — Auto-Waiting
Say: "The single most important feature. When you call await button.click(), Playwright doesn't just click. It runs through a checklist: Is the element attached to the DOM? Is it visible? Is it stable (not moving)? Is it enabled? Is it not obscured by another element? Playwright waits up to actionTimeout for ALL of these conditions. Only then does it click. In Selenium, you need: WebDriverWait(driver, 10).until(EC.element_to_be_clickable(locator)). In Playwright, that's automatic. This is why this entire framework has zero sleep() calls across 114 tests."
Anticipated Q&A
Q: "Why workers: 1? Doesn't that make tests slow?"
A: "Locally, speed isn't the priority — stability and predictability are. With one worker, tests share a single page, so no repeated logins. For scale, we use 4-shard CI with fail-fast: false. Parallel at the machine level, sequential within each machine."
Q: "What's the difference between testMatch and testIgnore?"
A: "testMatch is a whitelist — only match these files. testIgnore is a blacklist — match everything EXCEPT these. The api project uses testMatch (only API tests). The chromium project uses testIgnore (everything except api/setup/practice)."
Q: "Can I run a single test?"
A: "Yes. npx playwright test auth.spec.ts runs that file. npx playwright test -g 'Sign in' runs tests matching that name. npx playwright test auth.spec.ts:15 runs the test at line 15."
Common Pitfalls
Pitfall: Setting testIdAttribute wrong or forgetting it entirely. If the app uses data-test but Playwright defaults to data-testid, every getByTestId() call returns nothing — and your test times out with a generic 'locator resolved to 0 elements' error.
Pitfall: Setting actionTimeout higher than timeout. If your test has a 30s timeout but actions wait 60s, the test dies before the action finishes — and the error message says 'test timeout' instead of 'element not found.'
Key Takeaways
Key takeaways: (1) One config file controls everything. (2) Projects create execution lanes with dependency resolution. (3) Auto-waiting eliminates manual waits and sleeps. (4) Locators are lazy — they never go stale. (5) Timeout hierarchy: test > navigation > action > assertion. (6) testIdAttribute must match your app's actual attribute.

04Selectors & Locator Strategies~30 min
What to Show
Open: pages/signin.page.ts, then pages/transaction.page.ts, then pages/home.page.ts side by side if possible.
What to Say — Opening
Say: "A locator strategy is the #1 decision that determines whether your test suite is maintainable or a nightmare. Bad locators break when a developer changes a CSS class. Good locators survive complete UI redesigns. Let me show you the hierarchy we follow."
How to Explain — The Locator Priority Pyramid
Explain with this pyramid (draw it on a whiteboard or show on screen):
Priority (best → worst):

1. getByRole()     → semantic role (button, heading, link, textbox)
2. getByLabel()    → associated label text (for form fields)
3. getByText()     → visible text content
4. getByTestId()   → data-test attribute (stable, developer-added)
5. locator('css')  → CSS selector (fragile, last resort)
6. locator('xpath') → XPath (most fragile, avoid)
Say: "Each level down is more fragile and less semantic. getByRole('button', { name: 'Sign In' }) survives a CSS class rename, a component library swap, even a complete redesign — as long as there's still a button called 'Sign In.' But locator('.MuiButton-root.signin-btn') breaks the moment someone changes the CSS class."
How to Explain — Real Code, Strategy by Strategy
Show: pages/signin.page.ts — three strategies in one file:
// Strategy 1: Label-based — matches the HTML <label> element
readonly username = this.page.getByLabel('Username');
readonly password = this.page.getByLabel('Password');

// Strategy 2: Role-based — matches the element's ARIA role + accessible name
readonly submit = this.page.getByRole('button', { name: 'Sign In' });

// Strategy 3: Test ID — matches data-test="signin-error"
readonly error = this.page.getByTestId('signin-error');

// Strategy 4: CSS text selector — fallback for elements without good attributes
readonly usernameRequired = this.page.locator('text=Username is required');
Say: "Why getByLabel('Username') instead of getByTestId('username-input')? Because the label IS what the user sees. If a screen reader says 'Username,' that's the real name. If a developer renames the test ID, the label doesn't change. We test like users — by what's visible and accessible."
Show: pages/transaction.page.ts — the MUI pattern:
// MUI wraps <input> in a <div> with the data-test attribute
// getByTestId('amount-input') returns the DIV, not the INPUT
readonly amountInput = this.page.getByTestId('transaction-create-amount-input')
  .locator('input');  // chain to reach the actual input element

readonly descriptionInput = this.page.getByTestId('transaction-create-description-input')
  .locator('input');  // same pattern — every MUI input needs this
Say: "This is the #1 MUI/Material UI gotcha. The data-test attribute is on the wrapper div, not the input. If you getByTestId('amount-input') and call .fill('100'), it tries to fill a div — which is not fillable. The test times out with a confusing error. The fix: chain .locator('input') to drill down to the actual input element. We do this consistently across every MUI page object."
Show: pages/home.page.ts — CSS contains selector:
// data-test*= means "attribute CONTAINS this value"
readonly transactionItems = this.page.locator('[data-test*="transaction-item"]');

// This matches: data-test="transaction-item-1", data-test="transaction-item-2", etc.
// It's a pattern match — catches all items regardless of the number suffix
Say: "When the test ID has dynamic suffixes — like transaction-item-1, transaction-item-2 — the *= (contains) operator matches all of them. This is different from = (exact match) and ^= (starts with). It's a CSS attribute selector — standard web knowledge, not Playwright-specific."
How to Explain — Composite Locators
Show: Open utils/login.helper.ts:
const signinBtn = page.getByRole('button', { name: 'Sign In' });
const sidenav = page.getByTestId('sidenav-user-full-name');
await signinBtn.or(sidenav).waitFor({ timeout: 10_000 });
Say: "Three advanced locator compositions: .or() — matches the FIRST locator that appears. Used when you don't know the page state — is the user on login or already inside the app? Whichever element appears first wins. .and() — matches an element that satisfies BOTH conditions. Example: page.getByRole('button').and(page.getByText('Submit')) — only matches a button that says 'Submit.' .filter() — narrows a locator with additional criteria. userList.filter({ hasText: 'John' }) — from all user items, only the one containing 'John.'"
How to Explain — User Search in Transaction Page
Show: The selectUser method in pages/transaction.page.ts:
async selectUser(name: string): Promise<void> {
  await this.userSearchInput.fill(name);
  await this.page.locator('[data-test*="user-list-item"]')
    .filter({ hasText: name })
    .first()
    .click();
}
Say: "This is a chained locator pattern. Step 1: fill the search box with a name. Step 2: find all elements matching [data-test*='user-list-item']. Step 3: filter to only those containing the search name. Step 4: take the first match. Step 5: click it. Each step narrows the scope. It's like saying 'go to the shopping mall, find the clothing section, find shirts, find blue ones, pick the first one.' Each step reduces ambiguity."
How to Explain — When to Use Which Strategy
Explain this decision matrix:
Element type          → Best strategy
─────────────────────────────────────
Buttons               → getByRole('button', { name: '...' })
Form inputs           → getByLabel('...')
Links                 → getByRole('link', { name: '...' })
Headings              → getByRole('heading', { name: '...' })
Error messages        → getByTestId('...')
Dynamic lists         → locator('[data-test*="..."]')
MUI wrapped inputs    → getByTestId('...').locator('input')
Text content          → getByText('...')
Last resort           → locator('css=...')
Anticipated Q&A
Q: "Why not use XPath?"
A: "XPath is fragile — //div[3]/span[2]/input breaks when a developer adds a wrapper div. CSS selectors with test IDs are shorter, faster to evaluate, and easier to read. XPath has one valid use case: when you need to traverse UP the DOM tree (parent axis). CSS can't do that."
Q: "What if the app doesn't have data-test attributes?"
A: "Ask the developers to add them. This is a collaboration, not a battle. Stable test IDs benefit everyone — they decouple UI tests from CSS and component library changes. If developers refuse, fall back to getByRole and getByLabel — they're stable without developer cooperation."
Q: "How do I find the right locator for an element?"
A: "Use Playwright's codegen: npx playwright codegen localhost:3000. It records your clicks and generates the recommended locator for each element. Or use page.pause() in your test to open the inspector — hover over any element to see its best locator."
Common Pitfalls
Pitfall: Using nth(0) without a specific enough base locator. If you find 5 buttons and click .nth(0), adding a new button to the page silently changes which button you click. Always narrow first, index last.
Pitfall: Forgetting that getByText() does substring matching by default. getByText('Sign') matches both 'Sign In' and 'Sign Up.' Use { exact: true } for precision: getByText('Sign In', { exact: true }).
Key Takeaways
Key takeaways: (1) Priority: Role > Label > TestId > CSS > XPath. (2) MUI pattern: getByTestId('x').locator('input'). (3) *= for dynamic test IDs. (4) .or() for unknown state, .filter() for narrowing, .first() for lists. (5) Locators are lazy and auto-retry — they never go stale.

05Assertions & Soft Assertions~30 min
What to Show
Open: tests/e2e/auth.spec.ts and tests/e2e/transaction.spec.ts
What to Say — Opening
Say: "Assertions are where you say 'I expect this to be true.' But Playwright has TWO fundamentally different types, and knowing which to use is the difference between a test that flakes and a test that's rock solid."
How to Explain — Auto-Retrying vs Non-Retrying
Explain with examples from the actual tests:
// AUTO-RETRYING — polls the DOM up to expect.timeout (10 seconds)
await expect(page.getByTestId('sidenav-user-full-name')).toBeVisible();
await expect(page).toHaveURL(/\//);
await expect(transactionPage.alertSuccess).toBeVisible();
await expect(homePage.transactionItems).toHaveCount(5);
await expect(page.getByText('Username is required')).toBeVisible();

// NON-RETRYING — checks once, immediately
expect(res.status()).toBe(200);
expect(found).toBeDefined();
expect(match.status).toBe('complete');
expect(cookies.length).toBeGreaterThan(0);
Say: "The rule is simple: if the value comes from the DOM (a locator, a page URL), use auto-retrying assertions — expect(locator). They poll because the DOM is dynamic — elements appear, disappear, update. If the value is already in your hands (an API response, a database record, a variable), use non-retrying — expect(value). It checks once because the value isn't going to change. The dangerous mistake: using a non-retrying assertion on a DOM value. expect(await button.isVisible()).toBe(true) — this checks ONCE. If the button appears 500ms later, the test fails. The correct version: await expect(button).toBeVisible() — this retries for 10 seconds."
How to Explain — Common Auto-Retrying Assertions
// Visibility
await expect(locator).toBeVisible();
await expect(locator).toBeHidden();

// Text content
await expect(locator).toHaveText('exact text');
await expect(locator).toContainText('partial');

// Input values
await expect(locator).toHaveValue('entered text');

// Count (for lists)
await expect(locator).toHaveCount(5);

// URL
await expect(page).toHaveURL(/\/dashboard/);
await expect(page).toHaveTitle(/My App/);

// CSS
await expect(locator).toHaveClass(/active/);
await expect(locator).toHaveCSS('color', 'rgb(255, 0, 0)');
How to Explain — Soft Assertions
Say: "Normal assertions are hard assertions — the test stops at the first failure. Soft assertions continue on failure and report ALL failures at the end."
// HARD — stops at first failure
await expect(profile.name).toHaveText('John');     // fails → test stops here
await expect(profile.email).toHaveText('john@x');  // never reached
await expect(profile.phone).toHaveText('555-0123'); // never reached

// SOFT — continues, reports all failures
await expect.soft(profile.name).toHaveText('John');     // fails → continues
await expect.soft(profile.email).toHaveText('john@x');  // fails → continues
await expect.soft(profile.phone).toHaveText('555-0123'); // passes
// Test report shows: 2 of 3 assertions failed
Say: "Use soft assertions when validating multiple independent fields on the same page. A profile form has 10 fields — you want to know which ones are wrong, not just the first one. Without soft assertions, you fix one field, run again, discover the next failure, fix it, run again... With soft assertions, one run shows all 10 results."
How to Explain — Negation and Timeout
// Wait for element to DISAPPEAR
await expect(spinner).not.toBeVisible();
await expect(dialog).not.toBeAttached();

// Custom timeout for slow operations
await expect(locator).toBeVisible({ timeout: 30_000 }); // 30 seconds for heavy pages
Say: ".not is also auto-retrying. expect(spinner).not.toBeVisible() waits up to 10 seconds for the spinner to disappear. This is how you wait for loading states to finish — not with sleep, but with a negated assertion."
How to Explain — Real-World Analogy
Say: "Auto-retrying assertions are like checking if your Uber has arrived. You don't check once and give up. You keep looking out the window every few seconds for 10 minutes. Non-retrying assertions are like checking if you have your wallet. You either have it or you don't — checking again won't change the answer."
Anticipated Q&A
Q: "When should I NOT use soft assertions?"
A: "When the first assertion is a precondition for the rest. If 'user is logged in' fails, there's no point checking 'profile shows correct name.' The assertions are dependent — use hard assertions so the test fails fast with a clear root cause."
Q: "What's the difference between toBeVisible() and toBeAttached()?"
A: "Attached means the element exists in the DOM. Visible means it's attached AND has non-zero size AND isn't hidden by CSS. A display: none element is attached but not visible. Use toBeVisible for user-facing checks, toBeAttached for DOM structure checks."
Q: "Why does this framework have zero sleep() calls?"
A: "Because auto-retrying assertions handle timing natively. Instead of sleep(2000) then check, we just check — and the assertion retries for up to 10 seconds. If the element appears in 100ms, we save 1.9 seconds. If it takes 5 seconds, we still pass. Sleep either wastes time or isn't enough time."
Key Takeaways
Key takeaways: (1) DOM values → auto-retrying. In-hand values → non-retrying. (2) expect.soft() for multi-field validation. (3) .not for waiting on disappearance. (4) Never expect(await locator.isVisible()).toBe(true) — this defeats auto-retry. (5) Auto-retrying assertions are why zero sleep() works.

What to Say — Opening

How to Explain — The Abstract Base Class
Show: pages/base.page.ts — the full file:
import type { Page } from '@playwright/test';
import { SideNavComponent } from './components/sidenav.component';
import { TopNavComponent } from './components/topnav.component';

export abstract class BasePage {
  readonly sidenav: SideNavComponent;
  readonly topnav: TopNavComponent;

  constructor(public readonly page: Page) {
    this.sidenav = new SideNavComponent(page);
    this.topnav = new TopNavComponent(page);
  }

  abstract readonly path: string;
  abstract waitForLoaded(): Promise<void>;

  async open(): Promise<void> {
    await this.page.goto(this.path);
    await this.waitForLoaded();
  }

  currentUrl(): string {
    return this.page.url();
  }
}
Say: "Let me break this down piece by piece. Line 1: abstract class BasePage — the abstract keyword means you CANNOT create new BasePage(). You must extend it. This prevents someone from using BasePage directly — it's a blueprint, not a building. Lines 2-3: Composition — SideNavComponent and TopNavComponent are created in the constructor. Every page that extends BasePage automatically gets this.sidenav and this.topnav. This is composition over inheritance. We DON'T put 20 navigation methods in BasePage. We compose small, focused components. Lines 7-8: Abstract members — abstract readonly path and abstract waitForLoaded(). You literally cannot create a page object without defining these. TypeScript enforces it at compile time. This means every single page object has a known URL path and a readiness check. No exceptions. No 'I forgot to add waitForLoaded.' Lines 10-13: Template Method Pattern — open() calls goto(this.path) then this.waitForLoaded(). The algorithm is fixed in the base class. The specifics are defined by each subclass. This is the Gang of Four Template Method pattern."
How to Explain — A Concrete Page Object
Show: pages/signin.page.ts:
export class SigninPage extends BasePage {
  readonly path = '/signin';

  readonly username = this.page.getByLabel('Username');
  readonly password = this.page.getByLabel('Password');
  readonly submit = this.page.getByRole('button', { name: 'Sign In' });
  readonly error = this.page.getByTestId('signin-error');
  readonly usernameRequired = this.page.locator('text=Username is required');
  readonly signupLink = this.page.getByTestId('signup');

  constructor(page: Page) {
    super(page);
  }

  async waitForLoaded(): Promise<void> {
    await this.submit.waitFor();
  }

  async login(user: string, pass: string): Promise<void> {
    await this.username.fill(user);
    await this.password.fill(pass);
    await this.submit.click();
  }
}
Say: "Look how clean this is. path = '/signin' — done, URL defined. Locators as readonly properties — all defined in one place. waitForLoaded waits for the submit button — that's how we know the page is ready. And login() is a keyword method — three actions bundled into one semantic operation. A test calling signinPage.login('john', 'pass123') reads like a specification. It doesn't say 'fill the username input, fill the password input, click the button.' It says 'log in with these credentials.' That's the abstraction level tests should operate at."

Say: "The numbers tell the story. This framework has 10 page objects, 2 component objects, and 72 UI tests. How to Explain — Real-World Analogy
Say: "A page object is like a TV remote. You press 'Volume Up' — you don't care if it uses infrared or Bluetooth, if it sends signal code 0x3A or 0x4B. The remote abstracts the complexity. Anticipated Q&A
Q: "Should every page have its own page object?"
A: "Only pages that tests interact with. If no test navigates to the settings page, don't create SettingsPage yet. YAGNI — You Aren't Gonna Need It. Create page objects on demand, not speculatively."
Q: "Why readonly on locators?"
A: "Locators are immutable descriptors. A test should never reassign signinPage.username = somethingElse. readonly enforces this. It also signals intent: these are stable references, not mutable state."
Q: "Why not put assertions in page objects?"

Key Takeaways
Key takeaways: (1) Abstract base class enforces path + waitForLoaded() on every page. (2) Composition over inheritance — components are plugged in, not inherited. export class ApiError extends Error {
  constructor(
    message: string,
    public readonly status: number,
    public readonly url: string,
  ) {
    super(message);
    this.name = 'ApiError';
  }
}

export class ApiClient {
  constructor(
    private readonly request: APIRequestContext,
    private readonly baseUrl: string,
  ) {}

  async login(username: string, password: string): Promise<void> {
    const res = await this.request.post(`${this.baseUrl}/login`, {
      data: { username, password },
    });
    if (!res.ok()) throw new ApiError(`Login failed for ${username}`, res.status(), '/login');
  }

  async get<T>(path: string): Promise<T> {
    const url = `${this.baseUrl}${path}`;
    const res = await this.request.get(url);
    if (!res.ok()) throw new ApiError(`GET ${url} -> ${res.status()}`, res.status(), url);
    return (await res.json()) as T;
  }

  async post<T>(path: string, data: unknown): Promise<T> {
    const url = `${this.baseUrl}${path}`;
    const res = await this.request.post(url, { data });
    if (!res.ok()) throw new ApiError(`POST ${url} -> ${res.status()}`, res.status(), url);
    return (await res.json()) as T;
  }

  async patch(path: string, data: unknown): Promise<APIResponse> {
    return this.request.patch(`${this.baseUrl}${path}`, { data });
  }

  async delete(path: string): Promise<APIResponse> {
    return this.request.delete(`${this.baseUrl}${path}`);
  }

  async getRaw(path: string): Promise<APIResponse> {
    return this.request.get(`${this.baseUrl}${path}`);
  }
}
Say: "Let me point out three design decisions: 1. Generics (<T>): get<User[]>('/users') returns User[]. get<Transaction>('/transactions/123') returns Transaction. The same method handles different response shapes — TypeScript provides the type. 2. Custom ApiError: When a call fails, the error message includes the HTTP method, the full URL, and the status code. No more 'test failed with: Error' — you get 'ApiError: GET http://localhost:3001/users -> 500.' Debugging goes from 20 minutes to 20 seconds. 3. Two tiers: get<T>() parses JSON and throws on errors. getRaw() returns the raw response — use it when you want to assert on status codes, headers, or non-JSON responses. patch() and delete() return raw because they may return empty bodies."
How to Explain — API Tests in the Project

Use API tests for: (1) Backend contract validation — does the API return the expected shape? (2) Data setup/teardown — create test data via API before UI tests. (3) Status code verification — does /nonexistent return 404?"
Key Takeaways
Key takeaways: (1) Playwright has a built-in HTTP client — no external packages. (2) Typed responses with generics. (3) Custom ApiError with status + URL for debugging. (4) get<T> for JSON, getRaw for raw responses. (5) API tests run without a browser — fastest execution.

    page.getByTestId('user-onboarding-dialog'),
    async () => {
      // Step 1: click Next on welcome screen
      const nextBtn = page.getByTestId('user-onboarding-next');
      if (await nextBtn.isVisible({ timeout: 1_000 }).catch(() => false)) {
        await nextBtn.click();

      if (await nextBtn.isVisible({ timeout: 1_000 }).catch(() => false)) {

Common Pitfalls — Complete List
Pitfall: Forgetting yarn build before start:ci. Vite-based apps need pre-built files. The server starts but serves nothing. wait-on times out with no useful error.
Pitfall: Using http:// instead of http-get:// with wait-on. Default uses HEAD requests which some servers don't handle. One-word fix.
Pitfall: Storing seeded credentials in GitHub Secrets. Faker generates different users every run. Read from the database dynamically.
Pitfall: Hardcoding file paths that differ between local (rwa-app/) and CI (rwa-app-ci/). Use env vars with fallbacks.
Pitfall: Asserting hardcoded names ('Neha', 'Arvilla') from local seed data. Use dynamic assertions or read from the database.
Pitfall: Using HTML reporter for shards then trying to merge. merge-reports requires blob format. Add --reporter=blob to the test command.
Pitfall: Missing merge-multiple: true on artifact download. Without it, blob files end up in nested folders and the merge command can't find them.
Pitfall: Forgetting && !cancelled() on the merge job. Without it, the merged report is only generated when ALL shards pass — exactly when you DON'T need it.
Pitfall: Forgetting the & after yarn start:ci. The workflow hangs forever because the server process never exits.
Pitfall: Using npm install instead of npm ci. npm install can modify package-lock.json. npm ci installs from the lockfile exactly.
Pitfall: Not setting fail-fast: false on the matrix. One failing shard cancels all others, and you lose evidence.
Pitfall: Forgetting if: always() on artifact upload. Without it, you only get reports from passing runs — useless.
Key Takeaways
Key takeaways: (1) Two-tier pipeline: PR gate (fast, blocking, Chromium only) + nightly regression (comprehensive, all browsers, 4 shards). (2) 8-step app startup: clone → install → build → seed → read credentials → start with log capture → wait-on http-get:// with 120s timeout. (3) Dynamic credentials via $GITHUB_ENV — never hardcode seeded data in Secrets. (4) RWA_DB_PATH env var for portable file paths between local and CI. (5) Blob reporter for shards + merge-multiple: true + !cancelled() for reliable report merging. (6) Assert structure, not specific values — toBeVisible() and not.toBeEmpty() instead of toContainText('Neha'). (7) Branch protection enforces the gate. if: always() on artifacts. npm ci not npm install. (8) When tests pass locally but fail in CI: check paths, check seed data, check build steps, check Node version — in that order.
